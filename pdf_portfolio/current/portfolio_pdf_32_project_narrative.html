Ghost March: 출시작을 기준본으로 남기고 다시 설계

한국 무속 테마의 모바일 survival-like 프로젝트입니다. 처음 목표는 장르 핵심 루프를 끝까지 완성해 Play Store에 올리는 것이었고, 출시 이후에는 구조적 병목을 분리해 대량 적 처리 성능을 재검증하는 방향으로 이어갔습니다.

개발 목적

작은 범위라도 완성, 수상, 출시까지 가져가며 모바일 클라이언트의 전체 루프를 경험.

핵심 구성

웨이브, 경험치/레벨업, 무기, 특수기 커맨드, 보스, 저장, 일시정지, UI feedback.

차별화 판단

리듬게임/격투게임의 커맨드 입력을 궁극기 게이지 수급과 연결.

운영 확장

AAB release, Billing, App Update, localization, AdMob 문서화.

구조상 문제 인식
  • GameManager가 상태, 입력, UI, 저장, 일시정지까지 넓게 소유해 변경 영향 범위가 커졌습니다.
  • Weapon.Update()의 switch 기반 분기는 무기 추가 시 조건 분기가 계속 늘어나는 형태였습니다.
  • PoolManager prefab 배열 순서가 런타임 id 계약처럼 쓰여 씬과 코드 결합이 강했습니다.
재설계 방향
  • Legacy MonoBehaviour 구조는 출시 기준본으로 보존해 비교 대상을 남겼습니다.
  • Enemy, Bullet, Drop, Wave, Damage Event를 DOTS 수직 슬라이스로 분리했습니다.
  • MonoBehaviour는 입력, UI, 외부 서비스, 씬 부트스트랩 쪽으로 제한했습니다.

Ghost March: 성능과 운영에서 남긴 근거

출시 경험만 남긴 것이 아니라, 이후 문제를 측정하고 구조를 바꿔 어떤 차이가 나는지 기록했습니다. 수치는 “구조 변경이 왜 필요했는가”를 설명하는 근거로 사용했습니다.

9fps

Legacy 구조에서 1500 enemies stress scene 기준. 플레이 루프가 유지되지 않는 병목을 먼저 확인했습니다.

67fps

DOTS 수직 슬라이스로 이동/피해/렌더링을 분리한 뒤 4096 enemies 기준으로 다시 측정했습니다.

109.5ms → 14.92ms

CPU frame time을 기준본과 실험본으로 나눠 비교해, 구조 변경의 효과가 숫자로 남는지 확인했습니다.

691 → 4

렌더링 batch 폭증을 instancing 적용 범위로 좁혀 GPU/CPU 양쪽 비용을 같이 줄였습니다.

트러블슈팅 1: 적 이동 보정

적이 과밀집될 때 충돌을 무시하고 무리 안쪽으로 파고드는 문제가 있었습니다. Flow Field만으로는 경로가 난잡해져, 목표 방향은 유지하되 밀집 구간에서만 보정 벡터를 더하는 방식으로 분리했습니다.

트러블슈팅 2: 렌더링 선택

RenderMeshIndirect 도입 후 URP 2D와의 궁합으로 GPU 비용이 오히려 커졌습니다. 목표가 “최신 API 사용”이 아니라 안정적인 결과였기 때문에 측정값이 더 안정적인 DrawMeshInstanced 쪽을 유지했습니다.

트러블슈팅 3: UI 비용

UI Toolkit label.text를 매 프레임 갱신하며 패널 전체 re-render가 발생했습니다. 점수와 상태값이 실제로 바뀐 경우에만 label을 갱신하게 바꾸고, dirty 빈도를 줄여 GPU/CPU 시간을 함께 낮췄습니다.

운영 처리 범위

AAB manifest/version/signing, Billing permission, App Update runtime class, localization workflow를 release checklist로 관리했습니다. 출시 이후에도 바뀌는 값과 민감 정보는 코드 설명에서 분리했습니다.

판단 기준

성능 실험은 “무조건 DOTS 전환”이 아니라, 기존 출시본을 비교 기준으로 보존한 뒤 병목이 뚜렷한 부분만 수직 슬라이스로 분리했습니다. 결과가 나쁘면 되돌릴 수 있는 범위로 실험했습니다.

얻은 것: 출시한 코드를 “끝난 코드”로 두지 않고, 기준본과 실험본을 분리해 비교해야 구조 변경의 효과와 위험을 동시에 볼 수 있다는 점을 확인했습니다. 성능 개선은 기술 교체 자체보다 기준 장면, 측정 항목, 되돌릴 수 있는 변경 범위를 먼저 정하는 일이 중요했습니다.

Match3LogueLike: 검증 루프와 남은 리스크를 분리

기능 테스트가 통과해도 실제 모바일 화면에서 읽히지 않을 수 있습니다. 그래서 문서, 테스트 근거, 화면 QA를 다른 레이어로 분리했습니다.

작업 문서

GDD, 구조 문서, asmdef 구조, AI 협업 계획, 멀티 에이전트 운영 문서를 먼저 작성해 작업자가 바뀌어도 기준을 잃지 않게 했습니다. 문서는 설명용 산출물이 아니라 생성 코드가 따라야 하는 경계로 사용했습니다.

테스트 근거

RewardOverlayTests 10/10, SaveManagerPhase1SmokeTests 4/4 등 PlayMode/EditMode 결과를 따로 남겼습니다. 기능 단위 테스트와 통합 smoke test를 나눠, 실패했을 때 어느 레이어가 깨졌는지 먼저 보게 했습니다.

화면 QA

Simulator 화면에서의 가독성, 터치 영역, 보상 overlay 상태를 별도 기록으로 남겨 “테스트 통과”와 “사용 가능”을 분리했습니다. 모바일 portrait에서는 배치가 맞아도 손가락 영역과 텍스트 크기 문제가 따로 생겼습니다.

1. 설계GDD, 데이터 우선순위, 모듈 경계, 금지 규칙을 먼저 정합니다. 여기서 벗어난 제안은 구현 전에 걸러냅니다.
2. 생성AI 작업은 정해진 lane과 asmdef 안에서만 진행하게 합니다. Data layer에는 MonoBehaviour 참조를 허용하지 않았습니다.
3. 검증테스트, architecture scan, merge preview, git diff check를 분리합니다. 통과 기준이 하나로 합쳐지지 않게 했습니다.
4. 리뷰스크린샷과 화면 QA로 실제 플레이 화면의 문제를 다시 봅니다. 보상창, 터치 영역, 작은 텍스트를 따로 확인했습니다.
남은 리스크 처리

미완성 기능을 완성처럼 쓰지 않기 위해 구현된 범위, 테스트된 범위, 문서상 계획을 분리했습니다. 이 프로젝트의 핵심은 “현재 어디까지 안전한가”를 보이게 만드는 것이었습니다.

다음 프로젝트로 옮긴 기준

AI 협업은 속도보다 변경 통제 비용이 더 큰 문제가 될 수 있습니다. 그래서 이후 작업에서도 asmdef, namespace, interface, 테스트 근거를 먼저 세우고 기능을 붙이는 순서를 유지합니다.

얻은 것: AI 협업에서 중요한 것은 “AI가 할 수 있는 일”보다 “AI가 하면 안 되는 일을 막는 구조”였습니다. 생성 결과를 믿기 전에 경계, 금지 규칙, 검증 결과를 서로 다른 문서와 테스트로 남겨야 했습니다.

LostCone: 공개 개발에서 방향을 바꾼 팬게임

팬층을 대상으로 한 플랫포머 프로젝트입니다. 처음에는 퍼즐 요소가 있는 메트로배니아에 가깝게 생각했지만, 실제 유저층이 복잡한 게임 문법보다 세계관과 이스터에그를 기대한다는 판단으로 방향을 바꿨습니다.

개발일지 50회

커뮤니티에 진행 상황을 공개하며 반응을 확인.

플레이테스트 3회

구글 폼과 직접 플레이 반응으로 조작/난이도 확인.

DOTween

프롤로그, fade, 아이템 이동 연출에 활용.

목적

좋아하는 IP의 분위기를 플레이 가능한 형태로 만들고, 실제 팬층 반응을 보며 완성 방향을 조정하는 것.

구성

플랫포머 이동, 컷씬, 아이템, 레벨 진행, 감성 연출, 저장 기능, 플레이테스트 배포 흐름.

판단

난이도 높은 메트로배니아보다 팬층이 찾고 즐길 수 있는 힐링/탐색 방향이 더 맞다고 판단.

1. 공개 기록개발일지로 진행 상황을 공개하고, 팬층이 어떤 장면에 반응하는지 확인했습니다.
2. 테스트플레이테스트와 설문으로 조작, 난이도, 길찾기, 연출 이해도를 수집했습니다.
3. 방향 전환복잡한 퍼즐보다 이스터에그와 분위기 탐색을 강화하는 쪽으로 조정했습니다.
4. 구현 반영컷씬, fade, 아이템 이동, 저장 기능을 팬게임의 감성 유지에 맞춰 다듬었습니다.
얻은 것: 내가 만들고 싶은 구조보다 실제 플레이할 사람의 이해도와 기대를 먼저 봐야 한다는 점을 공개 개발 과정에서 확인했습니다.

LostCone: 간헐적 입력 중단을 코드 밖 상태까지 추적

같은 코드와 같은 커밋에서도 키보드 입력이 중단되는 문제였습니다. 코드 변경만 반복해서는 원인을 잡을 수 없었고, 플레이 모드의 Input System 상태를 직접 확인하며 원인을 분리했습니다.

1. 증상플레이 중 키보드 입력이 간헐적으로 끊기고, 같은 커밋에서도 재현 조건이 일정하지 않았습니다. 저장 데이터나 씬 전환 문제로 보였습니다.
2. 실패한 시도ActionMap 강제 활성화, polling 전환, sceneLoaded, Domain Reload, Library 삭제, git checkout을 차례로 확인했지만 증상이 사라지지 않았습니다.
3. 원인터치스크린 노트북에서 Input System이 Control Scheme을 Touch로 auto-switch하고 있었습니다. 코드 diff가 아니라 실행 환경 상태 문제였습니다.
4. 해결Keyboard&Mouse scheme 강제, prefab default scheme 변경, auto-switch 해제로 입력 장치를 고정했습니다. 이후 같은 장면에서 입력이 유지되는지 다시 확인했습니다.
왜 오래 걸렸는가

코드상 입력 처리만 보면 ActionMap, Update timing, scene load 순서 모두 의심할 수 있었습니다. 하지만 문제는 코드가 아니라 현재 연결된 장치와 Control Scheme 선택 상태였습니다. 코드만 되돌리면 해결될 것이라는 가정이 오히려 추적을 늦췄습니다.

다음 작업에서 바뀐 점

간헐적 문제를 만나면 먼저 런타임 Inspector, 장치 상태, project setting, prefab default 값을 같이 확인합니다. “코드가 같으면 동작도 같다”는 가정을 줄이고, 엔진 설정과 디바이스 상태를 체크리스트에 넣었습니다.

확인한 코드

InputAction, ActionMap 전환, Update polling, sceneLoaded 연결 순서를 확인했습니다.

확인한 엔진 상태

PlayerInput의 current scheme, prefab default scheme, project input settings를 비교했습니다.

확인한 환경

터치스크린 장치가 연결된 노트북에서 Touch scheme으로 전환되는 상황을 분리했습니다.

남긴 기준

재현이 불안정한 버그는 코드 변경 전에 런타임 상태를 먼저 기록합니다.

얻은 것: 재현이 흔들리는 버그는 코드 diff만 볼 것이 아니라 엔진 상태, 입력 장치, 실행 환경까지 관찰해야 합니다. 같은 소스라도 런타임에서 선택된 장치와 scheme이 다르면 완전히 다른 결과가 나올 수 있었습니다.

Cubika: 작게 완성하고 WebGL로 배포

수박게임류 병합 퍼즐에서 출발했지만, 원형이 아니라 정사각형 큐브의 회전, 낙하, 밀치기를 사용해 플레이 감각을 바꾼 프로젝트입니다. 짧은 기간에 완성해 itch.io에 WebGL로 올리고, 이후 모바일 조작과 수익화 scaffold를 보강했습니다.

WebGL 배포

itch.io에서 바로 플레이 가능한 형태로 공개.

밀치기 메커닉

떨어진 큐브의 첫 유효 충돌에만 밀치기 의도를 적용.

3초 grace

over-line cube가 3초 지속될 때만 game over.

광고/IAP 구조

Unity Ads, remove-ads product scaffold 추가.

개발 목적

작은 게임을 끝까지 완성하고, 빌드-업로드-피드백 보강까지 경험하는 것.

문제 해결

game over가 너무 즉시 발생하면 납득하기 어려워 countdown feedback과 grace period를 추가했습니다.

얻은 것

완성 후의 작업은 새 기능보다 입력, feedback, 일시정지, 확인 팝업 같은 사용성 보강이 중요하다는 점을 확인했습니다.

메커닉 판단

원형 병합의 예측 가능한 흐름을 그대로 복제하지 않고, 사각형 큐브의 회전과 밀치기로 불안정하지만 읽을 수 있는 물리 퍼즐을 만들었습니다.

출시 후 보강

MainMenu, pause popup, confirmation dialog, mobile controls, Unity Ads/IAP scaffold를 추가해 단순 업로드 이후의 운영 항목을 확인했습니다.

작업 방식

프로젝트마다 형태는 달라도 반복되는 기준은 같습니다. 먼저 목적과 경계를 정하고, 구현 후에는 테스트/영상/실제 화면/운영 문서로 결과를 다시 확인합니다.

1. 목적 정의게임을 왜 만들고, 어떤 결과가 완료 기준인지 먼저 정합니다. Ghost March는 출시, Match3는 구조 설계, LostCone은 팬층 피드백이 기준이었습니다.
2. 구조 분리asmdef, EventBus, interface, namespace, 문서로 변경 영향 범위를 작게 만듭니다.
3. 검증 분리테스트 통과, 성능 수치, 영상, visual QA, 플레이테스트를 서로 다른 근거로 분리합니다.
4. 회고 반영문제를 해결하고 끝내지 않고, 다음 프로젝트의 설계 기준으로 옮깁니다.
